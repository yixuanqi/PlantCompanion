# 07｜本地数据、商店、收藏与纪念花园

## 1. 三个核心概念，切勿混淆

- **Species / 品种**：如 `mint`、`mushroom`。一旦解锁永久保留；同一品种可以种很多代。
- **PlantInstance / 单个生命**：种下的某一株，唯一 `instance_id` 和 `generation`；死了永久死，`DEAD` 行不可修改为 `ALIVE`。
- **Seed / 种子库存**：是否拥有可以种的种子。v0.1 建议品种解锁后可反复选择，免费基础种子无限供给，避免货币不足无法继续。

## 2. 数据模型（概念级）

```text
Settings { schema_version, reminder_minutes, idle_sleep_minutes,
  active_hours, show_bubble, animation_level, always_on_top,
  quiet_hours_enabled, window_placement, timezone }

PlantSpecies { id, name, rarity, is_secret, unlock_rule_id,
  art_manifest_version, dialogue_set_id, shop_price }

PlantInstance { id, species_id, generation, state: ALIVE|DEAD,
  life_stage, active_elapsed_ms, cycle_id, growth_points,
  planted_at_utc, died_at_utc?, death_reason?, last_checkpoint_at_utc }

SleepSession { instance_id, reasons: set, started_at_utc,
  saved_active_elapsed_ms, ended_at_utc? }

DrinkConfirmation { id, instance_id, cycle_id, confirmed_at_utc,
  eligible_for_reward, coin_delta, idempotency_key }

WalletLedger { id, delta, reason, reference_id, created_at_utc }
Inventory { species_id, unlocked_at_utc, is_owned }
Memorial { instance_id, species_id, generation, planted_at_utc,
  died_at_utc, effective_alive_ms, drink_confirmations, final_growth_stage }
UnlockProgress { rule_id, progress_value, unlocked_at_utc? }
```

建议主生命和钱包事件存 SQLite + migration。不能仅通过前端 localStorage 存生命；不同 Tauri WebView 可能不共享状态。

## 3. 商店 v0.1

- 设置中设 `种子铺` 面板；展示两款首发植物的卡片与水滴币余额。
- **首发暂定“首次任选一株免费，另一种 6 水滴币解锁”**，主要验证收集 UI / 图鉴 / 生死循环；具体价格与免费策略尚待用户确认。
- 解锁是品种级的，购买或领取后不会因为这株死掉而重新锁定。
- 植物仍活着时“种植其他品种”按钮不可用，提示“这一株还在陪着你，下次换个伙伴吧”。
- 图鉴展示首发植物、已发现状态、最长存活、总养育代数；未知隐藏款仅用 `???` 剪影占位（可关闭整块隐藏款入口）。
- **隐藏款只预留数据字段和解锁规则接口**，不生产伪完成的隐藏款正式美术，也不作为 0.1 完工门槛。

## 4. 水滴币与成长（建议默认）

- 获得 1 枚水滴币：当次为本周期首次有效喝水确认且与上次有效奖励间隔 `>= 30min` 的活跃时间（暂定）；不按“越喝越多”无限奖励。
- 快速点击可以重置计时吗？**建议不能。**一次有效喝水确认的最小间隔暂定 `>=15min`，15 分钟内点击只显示鼓励或提示，但不重置计时、不发币。
- 成长点 `+1`：每次满足有效确认条件增长 1 点；睡眠时不增长；达到可配置阈值后解锁芽/叶/花的造型变化。
- 不能让用户为了刷币过量喝水。应用不提供具体每日饮水目标或医疗建议。
- 钱包 `balance = sum(ledger.delta)`，每条事件有唯一 `idempotency_key`。失败退款及日志也要事务化。

## 5. 死亡与纪念花园

- 死亡判定应是一次事务：`mark DEAD` + `insert Memorial` + `append LifeEvent`；同一生命只能出现一条正式死亡记录。
- UI 显示「小薄荷·第一代｜陪伴 X 天｜有效记录喝水 X 次」，推荐额外显示“实际活跃陪伴时间”以避免用户将暂停时段误解为受苦时间。
- 纪念文字温和，不责怪用户；不得出现“未喝水导致健康受损”的暗示。
- 重种：**只有用户主动点击种植才发生；枯死当天或以后均可选择，不自动重种，不强制次日，且至少一种免费种子始终可用**。不可复活死亡实例。不依赖午夜或次日本地日期。
- 用户也可通过导出将纪念卡保存为图片（P1），不依赖外部网络。

## 6. 读写事务与一致性

- UI 发起 `confirm_drink`, `purchase_seed`, `plant_seed` 必须附随机 request ID / 可重试幂等键。
- 先更新业务数据、后返回成功与触发动画；不要“先播放浇水效果再看是否成功”。
- 交易失败不修改余额，不重复发奖励，不产生半条纪念记录。
- 设置改动写入新版本配置快照；保留 schema_version 可升级；至少提供最近一次有效备份。

## 7. 统计定义（防口径歧义）

- `喝水次数`：用户主动确认“我喝水了”的有效事件数量，不是真实摄入水量。
- `有效活跃存活时长`：只计确认为活跃的时间，排除锁屏/休眠/离线/手动休息。
- `现实陪伴时长`：从种植到死亡的日历时间；作为纪念可同时显示但不要拿来判死。
- `连续成功`：至少完成 N 个有效周期；如果需引入“每天”的条件必须先定义本地日历边界。
